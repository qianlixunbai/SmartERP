# 要件仕様書

## SmartOA — 簡易 OA 承認フロー管理システム

---

## 1. はじめに

### 1.1 作成目的

本文書は、SmartOA 承認フロー管理システムの機能要件と非機能要件を詳細に記述し、開発・テスト・検収の基準として利用することを目的とする。

### 1.2 プロジェクト背景

企業内の日常的な承認（休暇、経費精算、残業など）は、従来、紙の伝票や断片的なインスタントメッセージツールに依存しており、非効率、紛失しやすい、追跡が困難といった問題がある。SmartOA は、軽量なオンライン承認ソリューションを提供する。

### 1.3 適用範囲

- 開発チーム：要件の詳細を理解し、実装の指針とする
- テストチーム：テストケース作成の基準とする
- ユーザー／レビュー担当者：機能の完全性を検収する

### 1.4 用語定義

| 用語 | 説明 |
|---|---|
| 承認テンプレート | 事前定義された承認ルール。フォームフィールドと承認フローノードを含む |
| 承認ノード | 承認フローにおける1つのステップ。誰が承認するかを定義する |
| 承認フロー | 申請が提出されてから最終的に承認／却下されるまでの全経路 |
| 直属上司 | 組織構造における従業員の直接の上位者 |
| 部門責任者 | 部門の責任者 |
| 会签 (COUNTER_SIGN) | ノード上の全承認者が同意して初めて次のステップに進む |
| 或签 (OR_SIGN) | いずれかの承認者が同意すれば次のステップに進む |
| 条件分岐 | 休暇タイプや日数などの条件に応じて、承認ノードを動的にスキップまたはトリガーする |
| タイムアウト自動エスカレーション | 承認がタイムアウトした場合に、指定されたアクション（転送／承認／却下）を自動実行する |

## 2. システム全体概要

### 2.1 製品視点

SmartOA は B/S アーキテクチャに基づく Web アプリケーションシステムであり、フロントエンドとバックエンドを分離したアーキテクチャを採用している。フロントエンドは Vue 3 + Element Plus で SPA を構築し、バックエンドは Spring Boot + MyBatis-Plus で RESTful API を提供する。データは MySQL 8 に保存される。

### 2.2 ユーザーロール

| ロール | 責務 | 権限レベル |
|---|---|---|
| EMPLOYEE（一般社員） | 申請の提出、個人の申請履歴の閲覧、自身の申請の取下げ | 基本 |
| MANAGER（管理者／承認者） | 承認待ちの処理、テンプレート管理、データエクスポート、レポート閲覧 | 高級 |

### 2.3 実行環境

- サーバー側：JDK 21 + Spring Boot 3.5.14
- データベース：MySQL 8.0+
- クライアント側：モダンブラウザ（Chrome / Firefox / Edge）
- ネットワーク：HTTP/HTTPS

## 3. 機能要件

### 3.1 ユーザー認証モジュール (AUTH)

#### 3.1.1 ログイン

| 要件番号 | AUTH-001 |
|---|---|
| 説明 | ユーザーがユーザー名とパスワードでシステムにログインする |
| 入力 | ユーザー名（username）、パスワード（password） |
| 処理 | ユーザーテーブルを検索して BCrypt パスワードを検証し、JWT Token を生成する |
| 出力 | `Result<Map>` に Token + ユーザー基本情報（パスワードを除く）を含む |
| 例外 | ユーザー名またはパスワードが誤っている場合は失敗メッセージを返す |
| Token 有効期限 | 24 時間（86400000ms） |

#### 3.1.2 認証インターセプト

| 要件番号 | AUTH-002 |
|---|---|
| 説明 | ログインインターフェースを除くすべての /api/* インターフェースで JWT 認証が必要 |
| 処理 | JwtFilter がリクエストをインターセプトし、Authorization ヘッダーの Bearer Token を検証する |
| 例外 | Token なし / Token 無効 / Token 期限切れ / ユーザー不在 → 401 |

#### 3.1.3 現在のユーザー取得

| 要件番号 | AUTH-003 |
|---|---|
| 説明 | クライアントは Token に基づいて現在ログイン中のユーザー情報を取得できる |
| 出力 | ユーザー ID、ユーザー名、氏名、ロール、部門、組織階層 ID |

#### 3.1.4 ユーザー一覧

| 要件番号 | AUTH-004 |
|---|---|
| 説明 | フロントエンドが全ユーザー一覧を取得する（承認者選択に使用） |
| 出力 | User[] 配列、password フィールドは @JsonIgnore で除外される |

### 3.2 承認テンプレート管理モジュール (TPL)

#### 3.2.1 テンプレート一覧

| 要件番号 | TPL-001 |
|---|---|
| 説明 | 管理者がすべての承認テンプレートを閲覧する |
| 権限 | MANAGER |

#### 3.2.2 テンプレート CRUD

| 要件番号 | TPL-002 ~ TPL-005 |
|---|---|
| 説明 | 承認テンプレートの作成、閲覧、編集、削除 |
| テンプレートフィールド | name（テンプレート名）、description（説明）、enabled（有効フラグ） |
| 削除ルール | テンプレート削除時に関連する承認ノードとフォームフィールドをカスケード削除する |

#### 3.2.3 承認ノード管理

| 要件番号 | TPL-006 |
|---|---|
| 説明 | 管理者がテンプレートに承認フローノードを設定する。ビジュアルなドラッグ＆ドロップ並べ替えに対応 |
| ノードフィールド | nodeName、sortOrder、approverType、approverId、signType、approverIds、conditionExpression、timeoutHours、timeoutAction、escalateToUserId |
| 処理 | 保存時にまず古いノードを削除し（参照をクリーンアップ）、その後新しいノードを一括挿入する。sortOrder は自動割り当て |

#### 3.2.4 承認者タイプ

| タイプコード | 解決ルール |
|---|---|
| DIRECT_LEADER | 申請者の directLeaderId を検索する |
| DEPARTMENT_HEAD | 申請者の departmentHeadId を検索する |
| SPECIFIC_USER | ノード設定の approverId（単独）／approverIds（並行）を使用する |

#### 3.2.5 署名モード（P2 新規追加）

| 要件番号 | TPL-008 |
|---|---|
| 説明 | ノードは3種類の署名モードをサポートする |
| タイプ | SINGLE（単独承認）、COUNTER_SIGN（会签、全員の同意で進行）、OR_SIGN（或签、いずれかの同意で進行） |
| デフォルト | SINGLE |

#### 3.2.6 条件分岐（P2 新規追加）

| 要件番号 | TPL-009 |
|---|---|
| 説明 | 承認ノードは SpEL 条件式をサポートし、条件を満たした場合のみトリガーされる |
| 変数 | leaveType（休暇タイプ）、days（休暇日数）、startDate、endDate |
| 例 | `days > 3` → 3日超の場合にこのノードを通る；`leaveType == '病假'` → 病欠の場合にこのノードを通る |

#### 3.2.7 タイムアウト設定（P2 新規追加）

| 要件番号 | TPL-010 |
|---|---|
| 説明 | ノードにタイムアウト自動処理ポリシーを設定できる |
| パラメータ | timeoutHours（タイムアウト時間数）、timeoutAction（ESCALATE/AUTO_APPROVE/AUTO_REJECT）、escalateToUserId（エスカレーション先） |

#### 3.2.8 フォームフィールド管理

| 要件番号 | TPL-007 |
|---|---|
| 説明 | 管理者がテンプレートのフォームフィールド定義を閲覧する |
| フィールドタイプ | TEXT / DATE / SELECT / TEXTAREA / NUMBER |
| SELECT オプション | JSON 配列形式で保存 |

### 3.3 休暇申請モジュール (LEV)

#### 3.3.1 申請提出

| 要件番号 | LEV-001 |
|---|---|
| 説明 | 従業員が休暇申請を提出し、システムが自動的に承認フローを開始する |
| 入力 | templateId、leaveType、startDate、endDate、reason |
| 処理 | 1. ユーザーの存在を検証 2. LeaveRequest を作成 3. 最初の条件を満たす承認ノードに進める 4. ノードモードに応じて currentApproverId を設定するか approval_task を作成する |
| 事前条件 | 申請者に直属上司が割り当てられていること |
| ステータス | PENDING |

#### 3.3.2 承認操作

| 要件番号 | LEV-002 |
|---|---|
| 説明 | 承認者が申請に対して承認または却下の操作を行う |
| 入力 | requestId、action（APPROVE/REJECT）、comment |
| 検証 | 1. 申請が存在すること 2. ステータスが PENDING であること 3. 操作者が一致すること（SINGLE: currentApproverId；並行: approval_task に PENDING タスクがあること） |
| 承認処理 | 単独→進行；或签→残りをスキップして進行；会签→全員完了したら進行 |
| 却下処理 | 承認を記録 → REJECTED に設定 → 並行タスクをスキップ → フロー終了 |

#### 3.3.3 申請取下げ

| 要件番号 | LEV-003 |
|---|---|
| 説明 | 申請者が承認完了前に申請を取り下げる |
| 権限 | 申請者のみ |
| 事前条件 | ステータスが PENDING であること |
| 処理 | ステータス → WITHDRAWN、並行タスクをスキップ、currentApproverId/currentNodeId/timeoutTime → null |

#### 3.3.4 承認転送

| 要件番号 | LEV-004 |
|---|---|
| 説明 | 現在の承認者が承認タスクを他者に転送する（SINGLE モードのみ） |
| 入力 | toUserId |
| 権限 | 現在の承認者 |
| 処理 | 転送先ユーザーを検証 → currentApproverId を変更 → 転送記録を書き込む |
| 制約 | 並行承認ノードでは転送をサポートしない |

#### 3.3.5 並行承認タスク照会（P2 新規追加）

| 要件番号 | LEV-010 |
|---|---|
| 説明 | 休暇申請の現在のノードにおける PENDING 承認タスク一覧を照会する |
| 出力 | ApprovalTask[] に approverId、status を含む |

#### 3.3.6 滞留修復（P2 新規追加）

| 要件番号 | LEV-011 |
|---|---|
| 説明 | currentApproverId が null で、かつ PENDING タスクが関連付けられていない滞留申請を修復する |
| トリガー | 手動で POST /api/leave/repair を呼び出すか、自動スケジュールで実行 |

#### 3.3.7 自分の申請一覧

| 要件番号 | LEV-005 |
|---|---|
| 説明 | 現在のユーザーが提出したすべての申請を閲覧する |

#### 3.3.8 承認待ち一覧

| 要件番号 | LEV-006 |
|---|---|
| 説明 | 現在のユーザーが承認する必要のある PENDING ステータスの申請を閲覧する（SINGLE + 並行タスクを含む） |
| 検索条件 | currentApproverId = 現在のユーザー OR approval_task に PENDING タスクがある |

#### 3.3.9 処理済み一覧

| 要件番号 | LEV-007 |
|---|---|
| 説明 | 現在のユーザーが処理した申請を閲覧する |

#### 3.3.10 申請詳細

| 要件番号 | LEV-008 |
|---|---|
| 説明 | 申請の完全な情報を閲覧する。timeoutTime、承認ノード設定を含む |

#### 3.3.11 承認記録

| 要件番号 | LEV-009 |
|---|---|
| 説明 | 申請のすべての承認操作記録を閲覧する（TIMEOUT_* システム自動操作を含む） |

### 3.4 タイムアウト自動エスカレーションモジュール (TMO) — P2 新規追加

#### 3.4.1 タイムアウトチェック

| 要件番号 | TMO-001 |
|---|---|
| 説明 | システムは5分ごとに PENDING 申請を自動スキャンし、timeout_time が期限切れかどうかをチェックする |
| トリガー | @Scheduled(fixedRate = 300000) |
| 処理 | タイムアウトした各申請に対して、ノードに設定された timeoutAction を実行する |

#### 3.4.2 タイムアウトアクション

| アクション | 説明 |
|---|---|
| ESCALATE | escalateToUserId にエスカレーションするか、現在のノードをスキップして次へ進む |
| AUTO_APPROVE | 現在のノードを自動承認し、残りの承認者をスキップして次へ進む |
| AUTO_REJECT | 申請を自動却下し、フローを終了する |

#### 3.4.3 タイムアウト記録

| 要件番号 | TMO-003 |
|---|---|
| 説明 | タイムアウト処理は ApprovalRecord に書き込まれる（approverId=0, action=TIMEOUT_*）。ログで追跡可能 |

## 5. 非機能要件

### 5.1 パフォーマンス

| 指標 | 要件 |
|---|---|
| インターフェース応答時間 | ≤ 500ms（単純クエリ） |
| ページ読み込み時間 | ≤ 2s |
| 定期タスク間隔 | 5 分（タイムアウトチェック） |

### 5.2 セキュリティ

| 要件 | 実装 |
|---|---|
| 認証 | JWT Bearer Token（jjwt 0.13.0） |
| パスワード保護 | BCrypt 暗号化（spring-security-crypto）。フロントエンドに返却しない |
| 権限昇格防止 | 操作前に身元を検証（取下げ=申請者、承認=現在の承認者／並行タスク） |
| CORS | フロントエンドのドメインのみクロスオリジンを許可 |

### 5.3 ユーザビリティ

- フォームはリアルタイム検証とエラーヒントを提供する
- 操作には成功／失敗のフィードバックがある（ElMessage）
- ボタンの状態は権限と連動する（権限がない場合は非表示）
- 承認プログレスバーがフロー内の位置を直感的に表示する
- タイムアウト警告バーが期限を通知する

### 5.4 保守性

- バックエンド：階層化アーキテクチャ（Controller → Service → Mapper）、統一レスポンス `Result<T>`
- フロントエンド：Pinia 状態管理 + API 層の分離
- データベース：マイグレーションスクリプトのバージョン管理（mysql-p0 ~ mysql-p5）
- グローバル例外処理：BusinessException + @RestControllerAdvice
